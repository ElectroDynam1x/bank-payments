# Сервис платёжных поручений

Учебный проект к курсовой работе «Настройка и администрирование деплоя в производственных
средах банковских систем» (дисциплина «Настройка и администрирование сервисного программного
обеспечения», РТУ МИРЭА).

Проект показывает, как веб-приложение банка доставляется в кластер Docker Swarm: сборка
образов, проверка в тестовом контуре, выпуск в промышленный контур без остановки сервиса
и автоматический возврат к предыдущей версии при сбое.

Все организации, счета и реквизиты в тестовых данных вымышлены.

## Состав системы

| Сервис | Образ | Назначение |
| --- | --- | --- |
| `gateway` | nginx 1.30 | Точка входа: TLS, заголовки безопасности, ограничение частоты попыток входа, распределение запросов между репликами |
| `frontend` | nginx 1.30 | Клиентская часть: одностраничное приложение на HTML, CSS и JavaScript |
| `backend` | Python 3.13, FastAPI | Серверная часть: REST API, аутентификация по JWT, роли, журнал аудита |
| `db` | PostgreSQL 17 | Хранение счетов, платёжных поручений, пользователей и журнала аудита |

Сети кластера: `edge` (шлюз, клиентская и серверная части) и `data` (серверная часть и СУБД,
без выхода во внешние сети). Наружу опубликован только порт шлюза.

Роли пользователей: операционист создаёт и изменяет поручения, контролёр исполняет или
отклоняет поручения, созданные другим сотрудником, аудитор только просматривает данные
и журнал аудита.

## Структура репозитория

```
backend/                 серверная часть
  app/                   код приложения (маршруты, модели, миграции, тестовые данные)
  tests/                 модульные тесты (pytest, SQLite в памяти)
  Dockerfile             многоэтапная сборка образа
  requirements*.txt      зависимости с зафиксированными версиями
frontend/                клиентская часть
  src/                   index.html, app.js, styles.css
  nginx.conf, Dockerfile
gateway/                 шлюз: nginx.conf, Dockerfile
deploy/
  stack.yml              описание стека для Docker Swarm
  env/stage.env          параметры тестового контура
  env/prod.env           параметры промышленного контура
  scripts/deploy.sh      развёртывание версии с ожиданием и откатом
  scripts/smoke.sh       проверка работоспособности после развёртывания
.gitea/workflows/ci-cd.yml   конвейер CI/CD
stand/                   учебный стенд: кластер из трёх узлов, реестр, балансировщик
tools/loadcheck.py       контроль доступности сервиса во время обновления
docker-compose.yml       локальный запуск без кластера
VERSION                  номер версии выпуска
```

## Локальный запуск

Нужны Docker и Docker Compose.

```bash
./stand/dev-secrets.sh          # секреты и самоподписанный сертификат в каталоге .local
docker compose up --build       # приложение: https://localhost:8443
```

Тестовые пользователи: `admin`, `operator`, `auditor`. Пароль лежит в файле
`.local/demo_password`.

## Проверка кода

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/ruff check .          # статический анализ
.venv/bin/python -m pytest      # 25 модульных тестов
```

## Версии и образы

Номер версии хранится в файле `VERSION`. Образ получает метку `<версия>-<коммит>`, например
`1.0.1-3f2a9c1`. Образы собираются один раз при отправке изменений в ветку `main`. Тег выпуска
`v<версия>` запускает развёртывание тех же образов в промышленный контур, повторной сборки нет.

Базовые образы берутся из внутреннего зеркала реестра (`BASE_REGISTRY`), поэтому узлам
кластера и сборочному узлу не нужен доступ в интернет.

## Развёртывание в кластере

```bash
export REGISTRY=registry.bank.local:5000
export DOCKER_HOST=tcp://prod-swarm-01:2376 DOCKER_TLS_VERIFY=1 DOCKER_CERT_PATH=<каталог с ключами>
export CA_CERT=<корневой сертификат> DEMO_PASSWORD=<пароль тестового пользователя>
deploy/scripts/deploy.sh stage 1.0.1-3f2a9c1
```

Сценарий `deploy.sh` выкладывает стек, ждёт перехода всех сервисов на новую версию и запускает
`smoke.sh`. Если кластер откатил обновление или проверка не прошла, сервисы возвращаются
к предыдущей версии, а сценарий завершается с ошибкой.

Параметры обновления заданы в `deploy/stack.yml`: реплики заменяются по одной, новая реплика
запускается до остановки старой, при сбое новой реплики кластер сам возвращает прежнюю
версию (`failure_action: rollback`).

## Контуры

| Параметр | Тестовый (`stage`) | Промышленный (`prod`) |
| --- | --- | --- |
| Стек | `bank-stage` | `bank-prod` |
| Адрес | `https://payments-stage.bank.local:8443` | `https://payments.bank.local` |
| Реплики серверной части | 1 | 3 |
| Реплики клиентской части | 1 | 2 |

Секреты (`db_password`, `jwt_secret`, `demo_password`, `tls_cert`, `tls_key`) создаёт
администратор сценарием `stand/create-secrets.sh`. В репозитории их нет.

## Конвейер CI/CD

Файл `.gitea/workflows/ci-cd.yml`, синтаксис совместим с GitHub Actions.

1. `test`: статический анализ (ruff) и модульные тесты (pytest).
2. `build`: сборка трёх образов и публикация в реестре.
3. `deploy-stage`: развёртывание в тестовый контур и проверка работоспособности.
4. `deploy-prod`: запускается тегом `v*`, проверяет наличие образов этого коммита в реестре,
   развёртывает их в промышленный контур и проверяет работоспособность.

Тег выпуска может создать только ответственный за выпуск: в репозитории включена защита
тегов `v*`. Ключи доступа к кластеру и реестру хранятся в секретах конвейера.

## Учебный стенд

Сценарий `stand/up.sh` поднимает на одной машине реестр образов, три узла Swarm
(контейнеры `docker:dind`, у каждого свой демон Docker) и балансировщик. Подробности
в `stand/README.md`.
